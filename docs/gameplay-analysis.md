# The Conjuror — 玩法分析报告

> 生成日期: 2026-05-10
> 基于对 Server (Node.js + Socket.IO) 和 Client (Unity/C#) 完整代码的审查

---

## 一、项目现状概览

"The Conjuror" (代码中也称 Project Conflux) 是一个受 MTG 启发的在线卡牌对战游戏。当前实现为一个 **仅限 2 人对战的功能原型**，服务器使用 Node.js + Socket.IO v2，客户端使用 Unity + C#。

### 当前可玩功能

- 2 人房间匹配与对战
- 回合制流程（抽牌 → 出牌 → 攻击 → 结束）
- 3 种卡牌类型：法术(Spell)、生物(Creature)、附魔(Enchantment)
- 5 个卡槽位（白/蓝/全/绿/红）
- 基于 slot 的群攻战斗系统
- Buff/Debuff 系统（削弱、禁锢）
- 两张需要目标选择的法术卡（Card1000004 选择卡槽、Card1000123 选择目标）
- 一个进场墓地触发效果的生物卡（Card1000011）

## 二、设计文档 vs 实现 —— 差距分析

### 2.1 核心资源系统：符文(Rune) vs 法力(Mana)

| 维度 | 设计文档 | 实际代码 |
|------|---------|---------|
| 资源名称 | 符文(Rune)，带颜色 | 法力(Mana)，单一整数 |
| 颜色系统 | 火焰/水流/空气/大地 四色符文 | 无颜色区分 |
| 费用机制 | 卡牌消耗特定颜色符文 (如 "火焰1, 大地2") | 卡牌消耗整数法力 |
| 激活符文阶段 | 每回合激活并选择一个新符文颜色 | 无此阶段 |

**影响**: 这是最根本的设计-实现偏离。失去了颜色匹配的策略深度，卡牌成本系统变成纯粹的数值门槛，四大元素的特色无法通过资源系统体现。

### 2.2 元素增强(Elemental Synchronized)

- **文档**: 生物卡颜色 = 卡槽颜色时获得 +1/+1
- **代码**: 完全未实现

### 2.3 回收(Cycling)

- **文档**: 可将战场生物回收进墓地，本回合获得同色额外符文
- **代码**: 完全未实现

## 三、架构问题

### 3.1 严重问题

**3.1.1 无游戏结束检测**
`Room.js` 中没有任何代码检测玩家生命值 ≤ 0。战斗伤害会改变生命值，但游戏永不结束。

**3.1.2 Power 字段双重职责**
`Card.power` 同时充当攻击力和生命值。伤害不仅削减"血量"，也降低攻击力 —— 这意味着受伤的生物会变弱，这在文档中并未说明，且与文档中"力量(Power)/防御(Defense)"的分离设计矛盾。

**3.1.3 伤害分配算法不合理**
`CardSlot.takeDamage()` 总是从力量最低的生物开始承伤。这意味着：
- 强生物可以躲在弱生物后面
- 如果攻击力不足以击杀最弱的生物，则所有伤害被吸收
- 玩家无法选择攻击目标（攻击是整个 slot 对 slot 的碰撞）

**3.1.4 全局可变状态**
```javascript
let guid = 0;  // 模块级全局，重启或热更新会重置
```
所有房间和客户端存储在进程内存中，无持久化，服务器重启即丢失所有游戏状态。

### 3.2 架构局限

**3.2.1 2 人硬编码**
`Room` 类用 `player1`/`player2` 字段硬编码。扩展到 3-6 人需要大量重构。

**3.2.2 无正式回合阶段状态机**
用 `turnStartEvents` / `turnEndEvents` 回调数组模拟阶段，但：
- 无法表达"激活符文阶段"这类中间阶段
- 无法在阶段间加入玩家交互
- 无法实现"响应"机制 (instant-speed)

**3.2.3 卡牌技能注册方式脆弱**
```javascript
// CardAbility.js
const CardAbility = {
    Card1000004: require('./Card1000004'),  // 手工注册
    ...
};
```
每加一张新卡就要手动导入，无法热加载。

**3.2.4 客户端数据结构过于简单**
`Card` 类 (C#) 只是数据容器，没有任何行为。所有卡牌效果由服务器通过事件驱动，客户端只是被动的渲染端。这简化了客户端但把全部逻辑压在服务器上。

**3.2.5 CrossScenePayload 模式脆弱**
客户端用静态 Queue 在场景切换时传递数据，场景顺序或并发问题极易导致数据混乱或丢失。

### 3.3 次要问题

- Socket.IO v2 (2017) 版本过旧
- 数据存储在 Excel 文件中 (`data.xlsx`)，不便于版本管理和多人协作
- 无任何测试
- 无数据库 / 无用户系统 / 无认证
- 无手牌上限
- 无 deck 构建界面（deck 预设硬编码）
- 中文注释与英文代码混用

## 四、玩法设计评价

### 4.1 现有亮点

- **元素克制链**: 火焰 > 水流 > 大地 > 空气 的四色克制关系提供了清晰的策略线索
- **卡槽颜色匹配**: 生物必须放置在正确颜色的卡槽中才能发挥效果，增加了站位策略
- **群攻战斗**: slot 级别的战斗结算简化了操作，降低了上手门槛
- **Buff 系统**: 有时间限制（回合结束消失）的 buff 机制基础扎实
- **目标选择流程**: `SELECT_TARGET → SELECT_SLOT → SELECT_DONE` 的异步目标选择流程设计合理

### 4.2 设计缺陷

**4.2.1 缺乏互动性**
当前没有"在对手回合响应"的任何机制。玩家回合是完全独立的，这使游戏变成了"各自拼数值"的 solitaire 体验。

**4.2.2 攻击系统缺乏选择空间**
- 每 slot 每回合只能攻击一次
- 攻击目标是 slot 整体，不能选择具体生物
- 伤害会自动分配给最弱生物

这导致战斗几乎不需要决策 —— 玩家只需选择攻击哪个敌方卡槽，其余自动结算。

**4.2.3 元素系统未被充分利用**
符文失去了颜色，元素增强未实现，位面相关关键词未实现 —— 导致四大元素的差异化停留在文档层面。

**4.2.4 卡牌生态极度贫瘠**
当前只有 5 张卡具有实际代码能力，且效果重复度高（两个是选择目标施加 debuff，一个是亡语抽牌，一个是无条件抽牌，一个是战斗减攻）。

**4.2.5 没有"召唤失调"**
生物登场即可以攻击，没有等待回合的限制。先手优势极大。

## 五、改进建议（按优先级排列）

### P0 — 必须修复

1. **实现游戏结束检测**: 生命值 ≤ 0 → 宣告失败 → 对方胜利
2. **分离 Power 和 Defense**: 生物需要独立的攻击力和生命值字段
3. **牌库抽空处理**: 抽空牌库应判定失败而非崩溃
4. **修复伤害分配逻辑**: 允许攻击方选择目标生物，或至少从最强生物开始分配

### P1 — 核心玩法补全

5. **实现颜色符文系统**: 将单一 mana 值改为多色符文资源池
6. **实现元素增强**: 颜色匹配卡槽时 +1/+1
7. **引入召唤失调**: 生物登场回合不能攻击（除非有 Haste 类关键词）
8. **实现 6 个核心关键词**: 伤害X、增幅X、生长X、位面行者X、自爆X、不稳定
9. **扩展玩家数量支持**: 重构 Room 为数组驱动的玩家列表
10. **增加手牌上限**: 回合结束时超过上限需弃牌

### P2 — 体验提升

11. **实现回收(Cycling)机制**
12. **增加卡牌数量**: 至少每种颜色 8-10 张不同效果的卡
13. **实现 mulligan 系统**
14. **实现回合阶段状态机**: Begin → Draw → Rune → Combat → End
15. **增加 deck 构建功能**
16. **升级技术栈**: Socket.IO v4，TypeScript 迁移

### P3 — 长期愿景

17. **引入 instant/响应机制**: 类似 MTG 的 instant speed，增加互动深度
18. **实现队伍系统**: 2v2、3v3 对战
19. **添加特殊胜利条件**: 配合文档中的"满足特定条件"获胜
20. **持久化**: 数据库存储，用户系统，战绩记录
21. **AI 对手**: 单机练习模式

## 七、技术债务清单

| 项目 | 严重度 | 说明 |

| 全局 guid 计数器 | 高 | 改用 UUID 或数据库自增 |
